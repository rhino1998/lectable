# API surface

Moved out of `../CLAUDE.md`. Every route, with the behaviour behind it.
`internal/httpapi` is the source of truth for the wire types and the route
table (the clients are generated from it); this is the prose that goes
with them.

- `POST /api/books[?play=on|off]` (multipart `file` - an epub (read as a play when it is one, `epub.ParseAs`; `play` overrides the detection), or a Lectable export - a whole-book one, or a latent-only transfer of some chapters (restored as its own book) - which restores that book: `409 book_exists` if it's already here) / `GET /api/books` / `GET|DELETE /api/books/{id}`
- `POST /api/books/import-url` `{"url", "previewId", "chapters"}` / `POST /api/books/import-url/preview[?url=|preview=][&archive=true]` (optional multipart `file`) / `POST /api/books/{id}/source/sync` / `POST /api/books/{id}/source/backfill` (multipart `file`) / `POST /api/books/{id}/source/reparse` / `POST /api/books/{id}/source/review` — **import from a website by link** (`httpapi/source.go`, `internal/websource`). The link picks the site: each one is a `websource.Source` (`Server.sources`: `internal/royalroad`, `internal/wanderinginn`), asked in turn whether the link is its own (`Match`) and then which work it means (`Resolve`); a link to no supported site is a `400` naming the ones that are. The import creates the book from the work's metadata, cover and *first chapter* and answers `201` with its summary like an upload - so it is in the library and readable at once - then fetches the rest in the background, as a job-queue task (`startSourceSync`: one `jobs.BulkGroup` per book, Kind `pipeline_source_sync`, key `source_sync`, `TierNormal`) - a Jobs-page row for every site alike, so a paused queue holds it and cancelling the row stops the check, keeping the chapters already added. Unlike an upload it queues nothing for the first chapter (no sample narration, no length estimate): links come in several at a time, and each would start rendering at once. `409 book_exists` if the library already has that work, `404` if the site doesn't, `502` if it can't be read. The second route ("Check for new chapters", `202`; `409` for a book with no source) runs the same pass again later. That pass (`syncBookSource`) re-reads the work's chapter list and appends, in the site's order, every chapter whose site id (`chapters.source_id`) the book doesn't have (`store.AppendChapters`, `sourceBatch` = 10 at a time): existing chapters, their attribution and audio are never touched, a retitled chapter isn't fetched twice, and a chapter published between two the book already has still goes at the end. **A chapter the site lists but won't serve** - early access, patrons only; flagged in the list (`ChapterRef.Unlocked`) or found on fetching it (`websource.ErrLocked`) - is looked for elsewhere, in this order (`readOrFill`): in the epub uploaded for this check, if there is one (below); then in the **Wayback Machine** (`websource.Wayback.ArchivedChapter`: the page's archived copies, newest first, thinned to at most 6 spread over its history, the first one the site's own parser reads as a chapter winning - i.e. the last copy saved while it was public; skipped for a chapter the list itself marks locked, which never was). With neither, the pass **stops there** and records the chapter's title (`source.blocked`, `books.source_blocked`, migration 00013), so a book never skips past a chapter and carries on from it once it opens. **Backfill** (`source_fill.go`, the third route; `202` with how many of the missing chapters the epub could stand in for, `422` if none, `409` while a check is running) runs one such pass with an uploaded epub at hand - the published volume: its chapters are matched to the site's by title key (letters and digits, "chapter" dropped), against the ebook titles the site's list gives for a chapter where it does (`ChapterRef.Aliases` - The Wandering Inn's table of contents has an ebook column, and the web and ebook numbering differ: web 1.01 is ebook 1.02) and its own title otherwise. One web chapter can be several ebook chapters (all appended, the first carrying its id) or share one with its neighbours (the chapter already appended also takes the neighbour's id - `chapters.source_id` holds several, space-separated). A chapter with no title to go by is placed by counting from chapters the epub is known to have - by a name only one of its chapters carries, or by **opening with the same text** as a chapter the book already has (`knowBook`, `store.ChapterOpenings`: the first ~700 characters as three-word runs, at least 45% shared and clearly ahead of the next best, so a published edition's copy-edits still match). With a known chapter either side, the two must sit exactly as far apart in the epub as in the source; with one on one side only, the chapter is counted on from it as long as the epub's story runs on unbroken (`runsOn`: its numbered chapters count up by one, nothing in between is front or back matter) - which is how a renumbered volume that only numbers its chapters ("Chapter 1" for the serial's chapter 70) is followed chapter by chapter from the last one the book has. An epub that shares nothing with the book (the next volume) needs telling where it starts: a `first` form field names the epub chapter (its index) that is the first one the book is missing, and the rest follow on. `POST /api/epub/chapters` (multipart `file`, optional `bookId`) lists an epub's chapters for that choice (`index`, `title`, `opening`, `paragraphs`, and `bookChapter` - the idx of the book's chapter with the same opening, if any), storing nothing. **Matching by hand**: `POST /api/books/{id}/chapters/{idx}/match-epub` (multipart `file`, `epubChapter`, optional `title`) replaces one existing chapter's content in place with the chosen epub chapter - for one filled from the wrong chapter. Its idx, source id and (by default) title stay, so nothing else moves; like a re-import it cancels the chapter's jobs and drops its audio, speakers and pass flags, and for a sourced book it rewrites the kept epub and the chapter's stored pages to match. Web only: Book settings → Chapters → "Match epub chapters" (`EpubMatchPanel`). **Rearranging a book's chapters** (`source_restructure.go`, store `restructure.go`; only for a book imported from a website, `409` otherwise or while its source is being checked): `POST /api/books/{id}/chapters/insert` (multipart `file`, `epubChapter`, `count` default 1, `at`, optional `title` for a single one) puts chapters of an epub in at idx `at`, the rest moving down - they get a source id of their own (`epub-…`), which no check asks the site about; `POST /api/books/{id}/chapters/{idx}/move` `{"to"}` moves one chapter; `DELETE /api/books/{id}/chapters/{idx}` removes one for good (a notice imported as a chapter, a duplicate), adding its source ids to the plan's `skip` so no check fetches it again. Only `chapters.idx` is renumbered - everything else about a chapter hangs off its id - and what names a chapter by idx follows it: the reading position and the recap's (a position inside a deleted chapter lands at the start of the next), with the book's sync tree dropped. The kept epub is rewritten to the new order (`websource.ArrangeEPUB`), so chapter re-import still reads the right chapter. No client UI yet. A filled chapter is written back out as markup (`epubChapterAsSource`: paragraphs, emphasis, table rows, images, breaks) and from there stored, kept and re-imported exactly like a fetched one; chapters the site does serve still come from the site. A chapter that answers 404 is passed over; any other failure stops the pass, keeping what was added. Nothing is queued for the new chapters - they generate when read, like any chapter. State is on the book summary (`source`: `kind`, `name`, `url`, `checkedAt`, `remoteChapters`, `error`, `blocked`, `syncing`), stored in `books.source_*` (migration 00012) except `syncing` (in memory: `Server.sourceSyncs`); `remoteChapters - chapterCount` is how many chapters a running or interrupted pass still has to fetch, so a pass cut short by a restart shows as chapters outstanding rather than nothing. Each chapter is parsed by laying it out as a one-chapter epub and running `epub.ParseAs` (never as a play), and everything fetched is kept as the book's source epub (`websource.WriteEPUB`: one spine file per chapter, each starting with its title as `<h1>` so an empty chapter still counts, plus an index of site ids in `META-INF/lectable-source.json` that lets a later pass add to the file) - so chapter re-import works from it as for an uploaded book, and a full export carries the link. A kept epub replaced by an uploaded file is no longer added to. Images a chapter embeds are downloaded (up to 24 a chapter, 10 MiB each) by a client that refuses non-public addresses; requests to a site go one at a time, 600 ms apart (`websource.Client`), so a 1,000-chapter serial takes about ten minutes. **Wayback Machine links** (`web.archive.org/web/<time>/<page of a supported site>`) import the work as archived then (`sourceReader`: the same `Source`, read through `Wayback.At(time)`, which fetches each address's copy nearest that time unaltered - `id_` - unpacking the ones saved gzipped and stepping to another nearby copy when one only redirects): its own book, titled "… (archived 2024-05-16)", with source kind `wayback` and id `<site kind>:<time>:<work id>`, so it sits beside the live work's book and a later check re-reads the same copy. The sites' parsers therefore read their older page layouts too. **archive.org items** (`archive.org/details/<item>`, or `/download/<item>/<file>`; `source_archiveorg.go`) are not a source: the item's freely downloadable epub (not a lent, encrypted one; up to 100 MiB) is fetched and imported as an upload would be (`Server.importEpub`), with nothing to check later. **Royal Road**: a work is a fiction (`/fiction/<id>`, or any of its chapter links); author's notes and the hidden filler the site mixes into chapter text are dropped, spoiler text kept. **The Wandering Inn**: the serial is far too long for one book, so a work is one *volume* of its table of contents (`vol-3`), imported as "The Wandering Inn: Volume 3" in the series "The Wandering Inn" (so the volumes share a character roster); a chapter link means the volume holding it, `…/table-of-contents/#vol-3` that volume, and the site's address or bare table of contents the first volume the library doesn't have. A chapter's id is its address's path. The closing author's note (with its reader art) and the previous/next links are dropped. The table of contents doesn't say which chapters are for patrons only - as of 2026-10 nearly all of volumes 1 and 2 are - so that is found on fetching one; those were public until early 2026, so the Wayback Machine has them. Until 2023 the table of contents was a plain list (`parsePlainTOC`) and until 2026 a chapter's text sat in `div.entry-content`; both are still read, for archived copies. **What a chapter was made from is kept** (`source_raw.go`): its page and the images it embeds exactly as fetched, before any cleaning (`websource.RawChapter` - the chapter as listed, whether it was read live, from the Wayback Machine or from an epub, and each response; recorded by a `websource.Recorder` around whichever fetcher read it), at `sources/<bookID>/<FileKey(source id)>.json.gz`; a chapter filled from an epub keeps the chapter itself, having no page. **Reparse** (the fourth route) reads every chapter again from those (`websource.Replay` - no network; an image that failed then fails now) with the current import code and rewrites the kept epub in place (`websource.RewriteEPUB`), answering `{"reparsed", "missing", "failed", "changed"}`: `missing` chapters have no stored pages (imported before 2026-10-07), and `changed` lists the chapter idxs whose text now differs from the library's. It changes no chapter itself - a changed chapter takes the new text through the ordinary chapter re-import, which is per chapter because it resets that chapter's speakers and audio. So a fix to a site's `parse.go` is applied with a reparse and then re-imports of the chapters it lists. No client UI; deleting a book removes its stored pages; exports don't carry them. **Preview and choosing chapters** (`source_preview.go`): the preview route resolves a link and answers the work's chapter list for the reader to choose from, each chapter with where its text would come from (`source`: `site`, `archive`, `epub`, `locked`), kept in memory under an `id` for two hours (`Server.importPreviews`). Asking again with `preview=<id>` widens it: `archive=true` searches the Internet Archive for **delisted chapters** - for a site that takes chapters off a work's list (`websource.Delister`; Royal Road's stubbed fictions) - via one prefix query to the archive's index for every chapter page it holds under the work's address (`Wayback.Delisted`; chapter ids come from the addresses, real titles from archived copies of the work's own page, up to 6 spread over its history plus 8 chosen by when still-untitled chapters were captured, the rest keeping a title made from the address slug), merged into the site's list in order (Royal Road: by chapter id, which follows writing order); a multipart `file` attaches an epub, whose chapters are preferred over the archive for delisted and locked chapters (same title matching as backfill). On He Who Fights With Monsters (2026-10-07) the site listed 19 chapters and the archive 1,021 more. The same search finds a chapter the site has **replaced in place** - an author overwriting a chapter with a notice or summary under the same id: the archive then holds that id under two addresses, and when the older one's title is nothing like what is listed now (`alike`: under half the shorter title's words shared, so a corrected typo or a cut-off address doesn't count) the earlier chapter joins the list just ahead of its replacement, with id `<id>@<old slug>` and `replacedBy` naming what took its place; both can be chosen. On The Legend of William Oh the site's "Book 1 Summary for RR" sits on what was chapter 37, which this recovers (135 listed, 196 from the archive, that one among them). An import naming `previewId` takes that list and only the `chapters` named (none = all), and turns the choice into the book's `store.SourcePlan` (`books.source_plan`, migration 00017): the ids left out (`skip`) and the chosen delisted chapters (`extra` - the site's list no longer names them, so a resumed or later check needs them written down). Every check works through `plannedChapters`: what the site lists now, less `skip`, with `extra` put back in place - so chapters published later are still added and ones left out stay out. A delisted chapter is read from the archive without asking the site; one the archive won't give is left out rather than stopping the check (nothing will ever open it at the site), reported in `source.error` and retried at the next check. Choosing applies to new imports only: chapters can't be inserted into a book that exists. **Reviewing what a check finds** (`source_review.go`, `POST /api/books/{id}/source/review` `{"import": [ids], "skip": [ids]}`, `202`): a site's chapter list isn't all story - authors post announcements, release notices and summaries in it - so a book takes only entries its reader agreed to (`SourcePlan.Approved`: the chapters chosen at import, then each one approved since). An entry a later check finds goes to `SourcePlan.Pending` instead, shown as `source.review` (`id`, `title`, `suspect`), and the check stops before the first one waiting - a chapter approved late would otherwise land after the ones that follow it. The reader says import or skip for each (skipped ids join `skip` for good; entries named in neither keep waiting) and a check runs. `suspect` (`suspectTitle`) marks a title that reads like a notice - one of a list of notice words (announcement, notice, hiatus, break, release, Kindle, Patreon, update, summary, "coming down"...) in a title that doesn't number itself as a chapter ("Chapter 12: Jail Break" is a chapter): unticked by default in the picker, pre-set to skip in a review, and held for review by an import that didn't use the picker - which takes the listed entries up to the first suspect and stops there. A plan from before reviewing existed (`reviewed` false) approves everything listed at its next check. Clients: the library's "Add book" → "Import from a link" (with "Choose chapters…" for the picker), the book's "Check for new chapters", and - on a book stopped at a locked chapter - "Fill locked chapters from an epub"
- `GET|PUT /api/settings/sources` `{"checkEveryHours"}` (live topic `sourceSettings`) / `POST /api/sources/check` — **checking sources unasked** (`httpapi/source_check.go`). `Server.CheckSources`, a `cron` task every 30 minutes, queues a check (`startSourceSync`) for each book imported from a website whose least recently checked source (`book_sources.checked_at`) is older than the library's interval - `default_voice.source_check_hours`, 24 by default, 0 never (migration 00018; the Settings pages' "New chapters"). Since a check only lists what is new for review, this imports nothing by itself: its effect is `source.review` filling up, which the clients mark the book's cover with (a bell and the count). `POST /api/sources/check` ("Check all for new chapters") queues a check for every sourced book whenever it was last checked, `202` with how many it queued.
- `POST /api/books/{id}/sources` `{"url"}` / `DELETE /api/books/{id}/sources/{sourceId}` — **several sources for one book** (`httpapi/source_multi.go`, table `book_sources`, migration 00021 - which moved the single source each book kept in `books.source_*` there as its first row). A book tracks any number of sources (`store.BookSources`, in the order added): the site it was imported from plus links added since - a serial's advance chapters on Patreon beside Royal Road, a site beside a Wayback copy of it - and a book from an uploaded epub can be given its first. Each row has its own check state and its own plan (`store.SourcePlan`: skip/approved/pending/extra, as before, plus `matched`).
  - **Adding** resolves the link like an import does, refuses a work some book already tracks (`409`, `book_exists` when it is another book's), stores the row with an empty reviewed plan and starts a check. Nothing is imported by adding: `201` with the source (`trackedSourceDTO`).
  - **Chapter ids.** A source added later gets `prefix` `"<site kind>:"` (none when it reads the same site as the book's unprefixed source, e.g. a Wayback copy of it, or when the book has no website chapters yet). The reader for that row (`readerForBook` -> `withPrefix`) puts the prefix on every chapter id coming out of the site and strips it going in, so `chapters.source_id`, the plan, the kept epub and `sources/<bookID>/` never see two sites' ids collide and nothing past the reader knows about prefixes. `readerForChapter` picks the reader for a stored chapter by its id's prefix (reparse, rename).
  - **One check, every source.** `startSourceSync` is still one job per book; it runs `syncBookSource` for each row in turn (each with its own `sourceSyncTimeout`) and stamps each row's `checked_at`/`error`. An uploaded epub (`.../source/backfill`) fills in for the first row that is stuck (blocked, or holding an unreadable chapter).
  - **The same chapter in two places.** Before anything is fetched, a source's entries the book doesn't have by id are compared with the chapters holding none of that source's ids (`otherChapters`): an entry and a chapter that share a `titleKey` nothing else on either side shares, and don't carry different chapter numbers, are the same chapter (`matchOtherSources`). An entry that gets past that and is fetched is compared by its opening text (`sameOpening`, 70% of three-word shingles) before being appended. Either way its id goes in the row's `plan.matched`, which counts as had from then on. Chapters from an added source are appended to the book's kept epub without renaming it (`websource.WriteEPUB` with an empty `Meta.Title`).
  - **Clients.** `BookSummary.source` stays the book-level roll-up the clients already used - `name` joined ("Royal Road + Patreon"), `review` every row's pending entries (each with its `source` name and `locked`), `error`/`blocked` the first row's that has one, `checkedAt` the oldest - and `source.tracked` lists the rows (`id`, `name`, `url`, `waiting`, `locked`, own `error`/`blocked`). `POST .../source/review` decides an id in whichever rows it waits in; deleting a chapter adds its ids to the skip list of every row that could list them. Removing a row (`204`) keeps its chapters; `409` for add/remove while a check runs. Web: Book settings → Chapters → Sources; Android: the library row's long-press "Add another source".
  - **Locked entries.** An entry a site lists but won't serve this reader (`ChapterRef.Unlocked` false: Royal Road early access, a Patreon post for patrons) is pending with `locked` set, and - unlike other pending entries - doesn't hold back what follows it (`reviewPlan`). The clients show these apart from the import/skip decision ("3 more at Patreon, locked"), so an untouched one is never skipped; agreed to, the check stops at it (`blocked`) until it opens.
- `PUT /api/books/{id}/sources/{sourceId}/title-rule` `{"pattern", "output", "only"}` — **a source's title rule** (`store.TitleRule` in the source's plan, `applyTitleRule` in `httpapi/source_multi.go`): a regular expression (Go/RE2) over the titles a source lists its entries under, for a source that posts more than chapters or names them its own way (Patreon). Every listed title is first cleaned (`cleanTitle`: line breaks, tabs, no-break and doubled spaces to one space, zero-width and control characters dropped - Patreon titles carry these), rule or no rule, and the pattern is matched against the title folded to NFKC as well (`foldTitle`: full-width and styled characters, ligatures, `…`), so a pattern typed on a keyboard matches; an output template is expanded from that folded text. An entry whose title matches is called what `output` - a template over the match's capture groups, `Chapter $1`, `${name}` - expands to (its own title when `output` is empty); with `only`, an entry that doesn't match is left out altogether: not imported, not offered for review. It is applied wherever a check builds the source's list (`plannedChapters`), so pending entries, fetched chapters and the title matching against the book's other sources all see the ruled titles; chapters the book already has keep their names. An empty pattern clears it; `400` for one that doesn't parse, `409` while the book is being checked; setting it starts a check. The same object is accepted as `titleRule` by `POST /api/books/import-url` (applied to that import too) and `POST /api/books/{id}/sources`, and reported per source as `source.tracked[].titleRule`. Web: the import form's chapter picker (with a live preview - `utils/titleRule.ts` mirrors Go's template syntax), and "Chapter names at <site>" in the pending-entries panel and under each source in Book settings → Chapters.
- `PUT /api/settings/patreon` `{"sessionId"}` — **Patreon** (`internal/patreon`, `httpapi/source_check.go`). Patreon's documented API (v2) only gives a creator their own posts - a member's token reads nothing, and Patreon has said it won't change that - so the source reads the JSON API the site's own pages use (`www.patreon.com/api/posts?filter[campaign_id]=...`, `/api/posts/<id>`, `/api/campaigns/<id>`, `/api/collection/<id>`, `/api/search` to turn a creator's page name into a campaign id). A work is a campaign (every post, oldest first, polls left out) or one collection of it (`"<campaign>/<collection>"`, from a `/collection/<id>` link). Signed out, that API still lists every post with its title and `current_user_can_view`, so a book can track a Patreon nobody is subscribed to: its chapters are listed, locked. Bodies are HTML (`content`, older posts) or a Tiptap document (`content_json_string`, converted by `tiptap.go`). Reading patrons-only posts takes the `session_id` cookie of a browser signed in as a member - the only way in, there being no OAuth for this - which this route checks against `/api/current_user` (`400` if Patreon doesn't know it), stores library-wide (`default_voice.patreon_session`/`patreon_account`, migration 00022) and gives the source, then re-checks every book tracking Patreon; `""` signs out. `GET /api/settings/sources` reports `patreonAccount`. The cookie is sent only to patreon.com. A cookie Patreon has since expired isn't refused, it just reads as a stranger - everything shows locked again. Verified against the live site signed out only (2026-10-09); the signed-in path follows what gallery-dl/yt-dlp do and is covered by `patreontest`, a stand-in. `WEBSOURCE_LIVE=https://www.patreon.com/<creator> PATREON_SESSION=<cookie> go test ./internal/websource -run TestLive -v` checks it for real. Web: Settings → Patreon.
  - **The same session unlocks The Wandering Inn** (`internal/wanderinginn/unlock.go`). wanderinginn.com keeps its newest chapters for patrons behind an "Unlock with Patreon" link - Patreon's login-with-Patreon consent page for the site. When a chapter page comes back locked and the library is signed in to Patreon, the source follows that link as the reader's browser would: `patreon.Source.Authorize` opens the consent page with the session and posts its form's "Allow" (refusing any link whose `redirect_uri` isn't the site's own host), Patreon answers with a redirect to `wanderinginn.com/patreon-authorization/?code=...`, and the source follows that - as a browser would, since the site drops the code for anything that doesn't look like one - keeping the cookies the site sets (`patreon_verified`, `patreon_tier_cents`, ...; they last a day), then reads the page again. Cookies live in memory only, sent only to wanderinginn.com; a lapsed login just triggers another unlock (at most one per 10 minutes - a page still locked sooner is a chapter the membership doesn't cover). `httpapi`'s `sources()` wires `wanderinginn.Source.Authorize` to the Patreon source; changing the Patreon session forgets the site's login and re-checks Wandering Inn books too. Verified against the live site 2026-10-09 (`WEBSOURCE_LIVE=<a newest chapter's link> WEBSOURCE_LIVE_LAST=1 PATREON_SESSION=<cookie> go test ./internal/websource -run TestLive -v`).
- `PUT /api/books/{id}/title` `{"title", "author"?}` — renames a book as the library shows it (`handleRenameBook`, `store.RenameBook`): the title (whitespace collapsed, not blank) and, when given, the author. Nothing else is keyed on either - files go by id, the character roster by series name - so no audio or attribution is touched. Web: Book settings → General; Android: the library row's long-press "Rename".

- `POST /api/books/{id}/chapters/{idx}/reimport[?force=true]` — re-parses one chapter from the book's source epub and replaces its content (`store.ReplaceChapterContent`), keeping every other chapter's attribution, fixes, and audio. The source is the copy kept at upload (`data/epubs/<bookID>.epub`, `audiopath.SourceEpubFile`), or an optional multipart `file`, which also replaces the kept copy. Cancels the chapter's queued/in-flight jobs first (`jobs.Manager.CancelChapter`). Resets the chapter's paragraphs, audio, SFX, music regions, images, breaks, and pass flags; bookmarks are re-pointed by idx. `?play=on|off` overrides play detection, as on upload. `409` with `code` `no_source_epub` (upload the file) or `title_mismatch` (retry with `force=true`), or plain `409` if the epub's chapter count differs or a job is still running
- `GET /api/books/{id}/manifest?chapters=0,3` — the root of the book's offline-sync hash tree (`httpapi/manifest.go`), for clients reconciling an offline copy (Android downloads) against the backend, which always wins: `hash` covers the book's title/author/cover (file size+mtime)/chapter count plus each listed chapter's `hash` (all chapters if `chapters` is omitted), returned in `chapters`. Built chapter hashes are stored in `sync_tree_nodes` (`Store.PutSyncTreeNodes`/`SyncTreeNodes`) tagged with a fingerprint of the rows they came from (`Store.SyncFingerprints`: one aggregate query per book over whole-row hashes (`rowhash`) of the book row minus position/estimate, its chapters/paragraphs/paragraph_audio minus `word_timings`/images/breaks, plus the whole character/voice tables) and with `syncTreeVersion` - a sha256 of the running `server` executable, since fingerprints can't see code (hash fields, DTO shapes, compiled-in voice presets) and Go builds are reproducible; nodes from other builds are pruned on the first manifest request. Only chapters whose rows moved get rebuilt. Validated by value on each request rather than invalidated by writes, since `OnChange` only knows tables, not rows: over-covering inputs can only cause a needless rebuild, never a stale hash. One row per chapter (primary key `book_id, chapter_idx`, upserted). Measured on the real library: a 244-chapter book's manifest goes from ~11.5s on first build to ~40ms afterwards (under DuckDB; under SQLite the fingerprint query alone is ~100ms for that book), including after a restart; a new build of `server` rebuilds each book once. Every chapter value (REST and the live `chapter` topic) carries its own `hash` plus per-paragraph `contentHash` (text/annotations an offline copy stores) and `audioHash` (resolved voice id, status, backing clip, duration, pointer) - so a client can tell "refresh metadata" from "re-download this .wav". Reading position is returned alongside but kept outside the tree
- `GET|POST /api/books/{id}/exports`, `GET /api/books/{id}/exports/{exportId}/file`, `DELETE /api/books/{id}/exports/{exportId}` — book exports (`internal/bookexport`, live topic `bookExports`). POST `{"format", "wordLevel", "phraseSeconds", "excludeMusic", "chapters", "asIs"}` queues a `jobs.BulkGroup` (Kind `pipeline_export`, key `export:<id>`, `202`): unless `asIs`, it first renders every not-ready paragraph of the chosen chapters (`jobs.Manager.RenderChapters`, failed ones retried) and waits, then builds - failing with "not fully rendered" if some paragraph still has no audio; `asIs` builds right away, missing audio text-only. Promoting the row promotes the audio it waits on. DELETE cancels the task and/or removes the file. The list overlays the job's queued/running state (`jobs.Manager.BulkState`) on the Manager's own.

- `POST /api/books/{id}/chapters/{idx}/generate-music` — queues the whole-chapter background-music run now (`jobs.Manager.GenerateChapterMusic`, `TierNormal`), regardless of the book's `musicEnabled` toggle; resets failed regions to pending first so they're retried. Each region carries a music prompt and an optional ambience prompt (the setting's soundscape - ocean, tavern, city - `""` for none), both written by `speakerattr`'s describe pass as structured fields and assembled in Go (scoring, `speakerattr.Client.ScoreMusic`: region starts are the chapter summary's scene starts - scenes under 5 paragraphs joined to the one before - plus a length-only split every 10 paragraphs, with no LLM call; a chapter with no summary is one region, split. Each region is then described by one call, shared with up to 2 of its length-only splits, which also decides `cut` via a `scene` field. Region starts used to come from an LLM pass over the whole chapter in 20-paragraph batches, dropped 2026-10-10: on 8 chapters it marked nothing past the opening in 6, where the summaries held 36 scenes. With the "same" answers below, the same 8 chapters on an idle GPU: 149 LLM calls -> 98, 147K prompt tokens -> 95K, ~12s -> ~8s a chapter, and 18 cuts -> 29, now on scene lines instead of 30-paragraph blocks) into Stable Audio 3's tag syntax (`buildMusicPrompt`/`buildAmbiencePrompt`). The two layers render as separate Stable Audio Medium calls and are served mixed (`musicgen.MixAmbience`, ambience level-matched a little under the music) - deliberately not one combined prompt, since SA3 tags each training clip as music *or* SFX and a mixed prompt tends to lose one layer and leaves no control over the balance. Ambience is one seamless 60s loop per distinct ambience prompt per book (`audiopath.AmbienceLoopFile`, rendered the first time a setting appears, tiled under every region set there at a region-derived offset - the describe pass answers `"same"` for an unchanged setting and gets the previous region's prompt back verbatim, so the same place hits the same file); it used to be re-rendered per region, continuation-seeded, which was about half of all music GPU time. The music layer's last 10s stays on disk (`audiopath.MusicRegionSeedFile`) so a `continuation` region seeds from it. Measured costs (Medium q8, warm, RX 7900 XTX): an unseeded 64s call ~2.6s, a 120s call ~4.6s - roughly linear, so seed length and loop margins are direct overhead; chunks are up to 110s and every clip renders only 4s past its served length for the loop crossfade. Batching the ambience loop with a music chunk (`batch_size=2`) was tried and dropped: the GPU is saturated at batch 1, and a batch renders both at the longer duration (18-25% slower when they differ). `202 {"queued": n}` (regions queued, 0 if all already have music), `409` if the chapter isn't scored or its narration isn't fully generated. Separately, `KindMusicLiveGeneration` tasks (one per region, keyed `music_live:<regionID>`, queued at `TierUrgent` since the reader is listening for them right now) chain forward from the reader's region as soon as each region's own paragraphs are voiced: a live task queues the next region's task the moment it dispatches, and that task depends on it (its seed clip) so it starts as soon as the first finishes - at most one live task per chapter is queued ahead, and a queued one the reader has moved past is canceled. The chain crosses chapter boundaries: past a chapter's last region it continues into the next chapter's first (waiting on the previous chapter's last live task for ordering, but not seeded from it), and an unscored next chapter gets its `ambience` task promoted to `TierLookahead` so the chain can cross once it's scored; reader-position lookahead only drives/promotes this live path (and scoring), never the whole-chapter batch, which stays `TierBackground` unless run explicitly; a region's "generating" state is tracked in memory (`Manager.MusicRegionGenerating`), never stored
- `POST /api/books/{id}/preprocess` — the "run everything" meta-task: scare-quote tagging, attribution, characterization, direction-tagging, and the ambience pass (music scoring + lighting) for every chapter/character in the book - LLM passes only: it no longer provisions voices (`httpapi.enqueuePreprocess` leaves `jobs.PhaseVoiceProvision` nil), a character's voice being made when a line of theirs is first generated or from the roster's own buttons. Phase dependencies are declared in `jobs.pipelinePhaseDeps`: scare-quote tagging before attribution, attribution before characterization, characterization before voice provisioning; direction-tagging and music scoring depend on none of them (`directChapter` only needs the book's own already-resolved voice and each paragraph's own `IsQuote`/`Text`, none of which the other three touch), so it dispatches immediately alongside attribution rather than waiting on the other three to clear first - see `jobs.pipelineResolver`'s own doc comment. `202 {"queued": 1}` immediately (503 if the LLM model file is missing, `409` if a run is already in progress for this book) - the four phases are real, dependency-ordered tasks (`jobs.Manager.EnqueuePipeline`, one `pipelineTask` per phase, `httpapi`'s `preprocess*Phase` closures supplying each phase's actual work), each phase task blocking on its own chapter's/character's real per-item task (`RunAttribution`/`RunCharacterization` via `ensureCharacterized`/`RunVoiceProvision`/`RunDirection`) exactly the way a single-item button dispatch already does - so no nested-queue-call deadlock risk (a phase task never occupies the `poolLLM`/`poolGeneration`/`poolDesign` slot it's waiting on). The phase tasks are scheduler tasks that need no pool (see `internal/jobs/pipeline.go`), so preprocessing runs alongside ordinary generation/attribution; the per-item tasks a phase asks for are adopted by it, so promoting or cancelling the phase reaches them. Progress observable exactly like the individual buttons' own. Best-effort and idempotent per item, so rerunning it (or an individual button) after a partial failure only redoes what didn't finish
